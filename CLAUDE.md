Read it before making non-trivial changes. This file only covers what's easy to get wrong.

## The hourly publish bot pushes from this clone

Windows Scheduled Task **"BFP Preview Publish"** runs `wscript.exe backend/run_publish_hidden.vbs` → `backend/run_publish.ps1` → `backend/publish.py` in this working copy, on two triggers: **every hour at about :18**, and **every 15 minutes (:00, :15, :30, :45) from 07:00 to 11:00 on weekdays** to pick up CEF's morning report quickly. The `.vbs` launcher keeps it from flashing a console window and stealing focus. Don't point the task straight at `powershell.exe`, because `-WindowStyle Hidden` doesn't prevent the flash. It rebuilds `docs/data/status.json`, then runs `git add` on that file, a plain `git commit`, and `git push`. Consequences:

- **Anything staged gets swept into the bot's "Update BFP preview data" commit.** Don't leave files staged; stage and commit in one step.
- **Any unpushed local commits get pushed** with the bot's commit. Don't leave half-finished work committed on `master`.
- **It commits to whichever branch is checked out.** Stay on `master`, or switch back well before :18. Otherwise data commits land on your feature branch and the push fails.
- **It never pulls.** If `origin/master` gets ahead (for example after an edit on github.com or a push from another machine), the bot's pushes fail until this clone is updated. Always push from this clone and `git pull --rebase` before pushing.
- Avoid committing or pushing between about :15 and :22, and on weekday mornings (07:00–11:00) also within a couple of minutes of :00, :30 and :45. Check `data/publish.log` for the last run's result.

## Background section: oil and the Strait of Hormuz (since 2026-10-09)

The last panel before "How this works" is supplementary context, deliberately placed below all the headline cards, charts and the table. **It never feeds the prediction.**

- Data: `backend/context_data.py` → `context` in the payload (`brent_futures`, `brent_spot`, `hormuz`, each `null` if never fetched). Brent futures = Yahoo `BZ=F` daily closes; physical = the EIA's daily Europe Brent spot (Dated Brent), scraped from `https://www.eia.gov/dnav/pet/hist/RBRTED.htm` (weekly releases, so a few days behind); Hormuz = IMF PortWatch daily transits for `chokepoint6` from its public ArcGIS feed (about 5 days behind, revised later). No API keys.
- Each part is cached in `data/context_cache.json` (gitignored) for 3 hours, since publish.py runs up to five times an hour. A failed fetch keeps the last good copy; `app.py` wraps the call so it can never stop a publish.
- "Normal before the conflict" is PortWatch's own average for the 365 days before `CONFLICT_START` (2026-02-28) in context_data.py, so both sides of the comparison come from the same source.
- **PortWatch undercounts during the conflict:** it only sees ships broadcasting AIS. In Sept 2026, Lloyd's List, Kpler and Windward (which add back "dark" crossings) counted roughly 3–5× more, and PortWatch's April–June tanker volume was 8% of pre-war against the EIA's 23%. The caveat box under the chart says so; keep it while the conflict lasts.
- Frontend: `context.js` is **identical** in `docs/` and `frontend/` (copy it across), builds the decorative tanker SVG (CSS keyframes `.tanker-art` in style.css, off under prefers-reduced-motion) and both charts. Each `app.js` calls `window.renderContext(state.data.context)` at the end of `render()`. The panel and each block hide themselves when their data is missing.

- **Backups:** the Windows Scheduled Task **"Project Backup"** runs `E:\Backup\Project_Backups\backup-projects.ps1` nightly at 02:00 (started through `backup-projects-hidden.vbs` via `wscript.exe` so no window flashes, the same approach as the publish task). - Python 3.10+, with Flask, requests, pdfplumber and numpy (`backend/requirements.txt`). There is no Node or build step.

- The whole design depends on your PC only making **outbound** connections to CEF, Yahoo Finance, GitHub, and (for the background section) eia.gov and IMF PortWatch's ArcGIS feed. Don't add anything that listens publicly or gives the public site a write endpoint.
- **Fuel levy changes are entered by hand** in `backend/fuel_levy.py` (since 2026-10-21: the MTBPS relief, R1.50 petrol / R3 diesel from 4 Nov 2026, then R1 / R1.50 to 5 Jan 2027). The payload's `levy_change` is the change on `predicted_change_date`; both `app.js` files and the month forecast page add it to the BFP forecast. `levy_relief` (the whole schedule) puts a cyan "Includes R1.50/l fuel levy relief" tag (`.levy-tag`) on any hero price with relief built in, and a `#levy-banner` under the fuel tabs explains it while any relief is announced or in force (it hides itself after the last period ends); the month pages mention it too. Check it against the DMPR's official price announcement each month, and add new announcements there.
- Values carry a `source` of `cef_official`, `estimated` or `manual`, and the UI must keep estimates visibly distinct from official figures.

### Monthly fuel price pages (since 2026-10-14)

`backend/month_pages.py` builds `docs/fuel-price/` (one page per price change, e.g. `/fuel-price/october-2026/`, a forecast page for the next change, and the history index `/fuel-price/`) and **rewrites `docs/sitemap.xml`**. Don't hand-edit those files: change the generator, then run `python month_pages.py` from `backend/`.

- **The bot runs it.** `publish.py` calls it after writing status.json (inside a try, so a failure never stops the data publish; its message goes to stdout because `run_publish.ps1` stops on any stderr) and always stages `docs/fuel-price` and `docs/sitemap.xml` with status.json. So a page or sitemap change you leave in the working copy goes out in the next "Update BFP preview data" commit.
- Past months come from CEF's reports cached in `data/bfp.db` (the price rows of the last report of each cycle, since CEF sometimes corrects one in a later report; the over/under recovery from the last report of the review period). A change effective on a date still ahead is written in the future tense until that day. Pages are only rewritten when their text changes, and only those get a new sitemap `lastmod`; the home page's `lastmod` is kept as it is in the sitemap, so still bump it there when the main page changes.
- The forecast page is a snapshot of status.json, renewed only when CEF publishes a new report or the review period closes (`data/month_pages_forecast.json`, gitignored), so it doesn't change every hour.
- **It never deletes.** If the cache no longer covers a month that's already published, it writes nothing and says so in the log.
- Styles: the pages load `/style.css` (the `?v=` is read from `docs/index.html`) plus a small `<style>` block in the generator. Prices are labelled the way `app.js` does (Gauteng pump price, wholesale, maximum retail).
- The main page links to `/fuel-price/` from the footer and the first FAQ answer.
- To remove the feature: `.\restore_month_pages.ps1` in `E:\claude_projects\seo_toolkit` (`-DryRun` first). It deletes `month_pages.py` and `docs/fuel-price/`, takes out exactly the lines that were added (the hook in `publish.py`, the two links in `docs/index.html`, the README lines, the `.gitignore` line and this section), resets the sitemap to the home page, and pushes; it stops without changing anything if any of those lines was edited since. So **if you change one of those lines, update `restore_month_pages.py` there to match.** The tag `before-month-pages` marks the state before.
